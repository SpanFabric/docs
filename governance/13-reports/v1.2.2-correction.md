# v1.2.2 BuilderKit Correction

## Trigger
A fresh independent pre-apply BREAKER against v1.2.1 returned `FINDINGS` with two concrete HIGH findings. The exact accepted input/evidence identity itself was valid, but Stage B was not authorized.

### F-000-01 — apply target scope was parameter-retargetable
The v1.2.1 repository/workspace scripts accepted arbitrary `-Org` / `-Root` values that could become durable GitHub/filesystem mutation targets. v1.2.2 introduces `11-bootstrap/fixed-targets.json` and enforces `SpanFabric` plus normalized `D:\Projekte\SpanGPU` before any mutation-capable GitHub/filesystem action. Parameters remain only for negative regression testing, not retargeting. A Windows PowerShell 5.1 regression uses a fake `gh` command and proves invalid targets fail before repository enumeration/creation; workspace-root mismatch fails before any `gh` invocation or filesystem mutation.

### F-000-02 — materialization could write before discovering a later conflict
The v1.2.1 materializer interleaved validation and writes. A late unmanaged conflict could therefore leave earlier repositories/files partially materialized. v1.2.2 splits planning from mutation:

1. **global read-only preflight** over all repositories/rules/destinations, including duplicate destinations, unmanaged conflicts, managed drift, version policy, state validity and path traversal;
2. **apply only after global preflight PASS**.

A failed preflight creates zero materialization files, zero materialization state, and zero apply journal. Apply requires a new immutable `--attempt-id` and creates an append-only journal under `_bootstrap-state/materialization-journal/`. Individual data/state writes use atomic replace. Repository state is written only after every desired file in that repository has been hash-verified. If I/O/process failure occurs after some writes, the journal remains and a **new-attempt** preflight can safely adopt only files whose bytes exactly match canonical desired sources; mismatches fail closed.
